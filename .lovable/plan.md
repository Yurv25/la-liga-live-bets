
# Migration: Lovable Cloud → Your Own Supabase Project

Target project: `https://lpvraykohdjkfiozsbde.supabase.co`

The goal is a minimal, reversible swap of the backend wiring. No UI changes, no edge function logic changes, no new features.

---

## Important caveat (read first)

Two files in this repo are **auto-regenerated by Lovable** every time it syncs with the managed Supabase:

- `src/integrations/supabase/client.ts`
- `src/integrations/supabase/types.ts`
- `.env` (also auto-managed; injects `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`)

If you stay inside Lovable, edits to these get overwritten. The clean way to migrate is therefore:

1. Introduce a **new client module** that we own: `src/lib/supabaseClient.ts`.
2. Re-export `supabase` from `src/integrations/supabase/client.ts` so existing imports (`@/integrations/supabase/client`) keep working — but if Lovable regenerates that file, your override is lost. So we also do a **codemod** of the 2 import sites to point at the new module directly. That makes the app independent of the auto-generated file.
3. Drive everything from a **new env file** (`.env.local`) using new variable names that Lovable does not manage: `VITE_APP_SUPABASE_URL`, `VITE_APP_SUPABASE_ANON_KEY`.
4. Once you run the project outside Lovable (locally / your own hosting), you can delete the `src/integrations/supabase/` folder and the Lovable `.env` entirely.


### 4. New: `src/lib/supabaseClient.ts` (the only client we own)
```ts
import { createClient } from '@supabase/supabase-js';

const url = import.meta.env.VITE_APP_SUPABASE_URL as string;
const anonKey = import.meta.env.VITE_APP_SUPABASE_ANON_KEY as string;

if (!url || !anonKey) {
  throw new Error(
    'Missing Supabase env vars. Set VITE_APP_SUPABASE_URL and VITE_APP_SUPABASE_ANON_KEY in .env.local'
  );
}

export const supabase = createClient(url, anonKey, {
  auth: {
    storage: localStorage,
    persistSession: true,
    autoRefreshToken: true,
  },
});
```

No generated `Database` type is imported — we drop the dependency on `src/integrations/supabase/types.ts`. The app currently uses `supabase.functions.invoke('laliga-matches')`, which doesn't need typed tables.

### 5. Codemod the 2 import sites
Currently only `src/lib/api.ts` (and the auto-gen client itself) reference `@/integrations/supabase/client`.

Change in `src/lib/api.ts`:
```ts
// before
import { supabase } from '@/integrations/supabase/client';
// after
import { supabase } from '@/lib/supabaseClient';
```

(Verified by grep: `src/lib/api.ts` is the only runtime import. If a second one exists elsewhere, the migration step will sweep it the same way.)

### 6. Move edge function config

Edit `supabase/config.toml`:
```toml
project_id = "lpvraykohdjkfiozsbde"
```

The function source `supabase/functions/laliga-matches/index.ts` is **not modified** — its logic, CORS, and Bzzoiro call stay exactly as-is.

### 7. Add npm scripts for local Supabase workflow

Add to `package.json` `scripts`:
```json
"supabase:start": "supabase start",
"supabase:stop": "supabase stop",
"supabase:link": "supabase link --project-ref lpvraykohdjkfiozsbde",
"functions:serve": "supabase functions serve laliga-matches --env-file ./supabase/.env",
"functions:deploy": "supabase functions deploy laliga-matches --project-ref lpvraykohdjkfiozsbde",
"secrets:set": "supabase secrets set --env-file ./supabase/.env --project-ref lpvraykohdjkfiozsbde"
```

### 8. New: `supabase/.env.example` (committed) and `supabase/.env` (git-ignored)

## Deployment steps for you to run (after the plan is implemented)

Inside Lovable's exec we cannot install the Supabase CLI or call your Supabase project. Run these on your machine:

```bash
# 1. Install CLI (one-time)
brew install supabase/tap/supabase   # or scoop / npm i -g supabase

# 2. Login + link
supabase login
supabase link --project-ref lpvraykohdjkfiozsbde

# 3. Push the Bzzoiro key as a function secret (server-side, never in git)
echo "BZZOIRO_API_KEY=<your key>" > supabase/.env
npm run secrets:set

# 4. Deploy the function
npm run functions:deploy

# 5. Smoke test
curl -i -X POST \
  "https://lpvraykohdjkfiozsbde.supabase.co/functions/v1/laliga-matches" \
  -H "Authorization: Bearer <YOUR_ANON_KEY>" \
  -H "apikey: <YOUR_ANON_KEY>"
```

For local dev:
```bash
npm run supabase:start          # starts local stack
npm run functions:serve         # serves the function locally with secrets
npm run dev                     # Vite picks up .env.local → hits your project
```

## Why this is safe / incremental

- Frontend still calls `supabase.functions.invoke('laliga-matches')` — unchanged.
- Edge function code is untouched; only `project_id` in `config.toml` changes.
- `BZZOIRO_API_KEY` stays a server-only secret (set via `supabase secrets set`, never in client env).
- New env var names (`VITE_APP_SUPABASE_*`) prevent Lovable's auto-regen of `.env` from clobbering your config.
- Rollback = revert `src/lib/api.ts` import + `supabase/config.toml` `project_id`.
